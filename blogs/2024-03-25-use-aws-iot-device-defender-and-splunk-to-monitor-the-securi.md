<p>With the growing adoption of Internet of Things (IoT) applications in regulated industries, such as healthcare, hardening IoT security devices has become a requirement. In addition to ensuring that backend systems are resilient, organizations increasingly invest effort to secure devices outside the traditional enterprise perimeter with <a href="https://en.wikipedia.org/wiki/Zero_trust_security_model">zero trust principles</a>. For example, fleet operators for connected medical devices need to ensure that the product does not exhibit anomalous behavior and function as designed. When a device’s security posture is compromised, it’s vital that these events are efficiently identified, analyzed, and managed by a centralized security team to safeguard the delivery of end-to-end patient care.</p> 
<p><a href="https://aws.amazon.com/iot-device-defender/">AWS IoT Device Defender</a>, a fully managed cloud service, continuously monitors IoT fleets to detect any abnormal device behavior, trigger security alerts, and provide built-in mitigation actions. This service can audit device-related resources against AWS IoT security best practices, and evaluate device-side and cloud-side metrics in near real-time against a predefined threshold. You can then receive alerts when AWS IoT Device Defender detects deviations. AWS IoT Device Defender also has a feature called <a href="https://docs.aws.amazon.com/iot/latest/developerguide/dd-detect-ml.html">ML Detect</a> that monitors metrics in near real-time, and applies machine learning (ML) algorithms to detect anomalies, and to raise alerts.</p> 
<p>AWS Partners, such as <a href="https://www.splunk.com/">Splunk</a>, provide security information and event management (SIEM) solutions that enable organizations to detect and respond to incidents in near real-time. A security solution that integrates AWS IoT Device Defender with the Splunk Platform can enhance your organization’s security posture by delivering data-driven cyber security to end-to-end IoT applications.</p> 
<p>In this blog, we illustrate how you can use AWS IoT Device Defender, <a href="https://aws.amazon.com/firehose/">Amazon Data Firehose</a>, and the Splunk Platform to ingest security-related metrics from IoT devices into a centralized SIEM. We also discuss how you can configure the security system to quickly identify risks and systematically measure their impact.</p> 
<h2>Solution overview</h2> 
<p>This is a fully serverless solution consisting of <a href="https://aws.amazon.com/iot-core/">AWS IoT Core</a>, <a href="https://aws.amazon.com/iot-device-defender/">AWS IoT Device Defender</a>, <a href="https://aws.amazon.com/firehose/">Amazon Data Firehose</a>, and the <a href="https://www.splunk.com/en_us/products/platform.html">Splunk Platform</a>.</p>

<p>The solution’s primary audience:</p> 
<ul> 
 <li>IoT application developers are responsible to develop and release new features. Their objective is to maximize their time writing robust code that delivers business value. While security is paramount, they don’t want to spend time writing custom code that extracts, processes, and transmits metrics that are relevant for security professionals to analyze system operations.</li> 
 <li>Security operations center (SOC) analysts are responsible to identify and react to security threats, and safeguard business operations. They use centralized SIEM tooling to monitor and gather intelligence on near real-time risks. They also enact manual and automated processes to strengthen the organization’s security posture.</li> 
</ul> 
<h2>How this solution works</h2> 
<ol> 
 <li>The IoT application is built using the <a href="https://docs.aws.amazon.com/iot/latest/developerguide/iot-sdks.html#iot-sdk-device-client">AWS IoT Device Client</a> so that supported <a href="https://docs.aws.amazon.com/iot/latest/developerguide/detect-device-side-metrics.html">device-side metrics</a> are sent automatically. The SDK publishes these metrics to AWS IoT Core <a href="https://mqtt.org/">Message Queueing Telemetry Transport (MQTT)</a> topics reserved for use by AWS IoT Device Defender. Supported device-side metrics include <em>established TCP connections count</em>, <em>listening TCP ports</em>, <em>destination IP addresses</em>, and the <em>number of outbound packets</em>.</li> 
 <li>AWS IoT Device Defender processes device-side metrics alongside <a href="https://docs.aws.amazon.com/iot/latest/developerguide/detect-cloud-side-metrics.html">cloud-side metrics</a>. Supported cloud-side metrics include <em>number of authorization failures</em>, <em>source IP address</em>, <em>connection attempts</em>, <em>message size</em>, <em>messages sent</em>, <em>messages received</em>, <em>disconnects</em>, and <em>disconnect duration</em>. Cloud-side metrics are generated regardless of the presence of device-side metrics.</li> 
 <li>The security profile of AWS IoT Device Defender’s detect feature is configured to publish the metrics to a user-defined MQTT topic. You can use this feature to configure rules and actions in AWS IoT Core to process and forward the metrics to other event consumers.</li> 
 <li>AWS IoT Core rules and actions are then configured on the MQTT topic to send the metrics to an Amazon Data Firehose delivery stream. In this design, Firehose provides a scalable data streaming pipeline that is capable of batching, buffering, and transforming payloads.</li> 
 <li>AWS IoT Device Defender’s audit feature can send audit findings to an Amazon Simple Notification Service (Amazon SNS) topic. The Amazon Data Firehose delivery stream subscribes to the Amazon SNS topic and receives the audit reports in its stream. <a href="https://docs.aws.amazon.com/iot/latest/developerguide/device-defender-audit-checks.html">Supported audit checks</a> include monitoring <em>overly permissive roles</em>, <em>shared device certificates</em>, and <em>conflicting MQTT client IDs</em>.</li> 
 <li>The solution then uses an AWS Lambda function within the streaming pipeline to transform the source records into a format that the SIEM solution can digest. This example adds a unique <code>sourcetype</code> key to the payload and restructures it under an <code>event</code> key. This makes the events easier to index and identify when searching through Splunk’s <a href="https://docs.splunk.com/Splexicon:SPL">Search Processing Language (SPL)</a>. Lambda provides flexibility to modify the data structure to align with downstream consumer requirements. For example, the Lambda function could further enrich the data by pulling device ownership information from a configuration management database (CMDB).</li> 
 <li>Amazon Data Firehose sends events to <a href="https://docs.aws.amazon.com/firehose/latest/dev/create-destination.html">supported destinations</a>. Both device-side and client-side metrics, as well as audit findings, are ingested into the SIEM solution via the Amazon Data Firehose delivery stream.</li> 
 <li>SIEM solutions, such as Splunk, support log ingestion from a large number of sources, including other AWS services, cloud workloads, and on-premises workloads. This holistic data aggregation allows the SOC to have full visibility into the organizational security posture – not just the silos where they have access.</li> 
 <li>SOC analysts can use the array of features available in an overarching SIEM solution. For example, if you use the Splunk Platform, you can use <a href="https://www.splunk.com/en_us/products/enterprise-security.html">Enterprise Security</a> and <a href="https://www.splunk.com/en_us/products/splunk-security-orchestration-and-automation.html">Security Orchestration, Automation and Response (SOAR)</a> to explore, analyze, and react to incoming data. &nbsp;You can use dashboards to visualize device-side and cloud-side metrics alongside other logs. You can use queries to aggregate, enrich, and search through the metrics. You can also automate responses using playbooks. For example, if a network port is unintentionally left open, you can detect if a device’s security posture has been weakened. If it has, you can assess the risk to the wider environment.</li> 
</ol> 
<h2>Deploying the solution</h2> 
<p>An <a href="https://aws.amazon.com/serverless/sam/">AWS Serverless Application Model (SAM)</a> template is available to deploy all AWS resources required by this solution, including the Python code used by the Lambda function. This template can be found in the <a href="https://github.com/aws-samples/aws-iot-device-defender-and-splunk/">aws-iot-device-defender-and-splunk</a> GitHub repository.</p> 
<p>Refer to the <a href="https://github.com/aws-samples/aws-iot-device-defender-and-splunk/">README</a> file for required prerequisites, deployment steps, and ways to test the solution.</p> 
<h2>AWS IoT Device Defender configurations</h2> 
<p>Once the solution is deployed, AWS IoT Device Defender configurations facilitate the metrics and audit reports publishing to Firehose.</p> 
<h3>Metrics</h3> 
<p>Navigate to the AWS IoT Console. Expand <strong>Detect</strong> in the Navigation pane and the choose <strong>Security profiles</strong>. Notice there is a security profile for you. The <strong>Additional metrics to retain</strong> tab contains a list of preconfigured metrics.</p>

<h2>Analyzing the events</h2> 
<p>Once the security data is ingested into the SIEM solution, the SOC analyst works to understand and assess the risks presented within their environments. In this example, we use the Splunk Processing Language (SPL) to perform this analysis.</p> 
<h3>Metrics</h3> 
<p>Once the solution generates data, navigate to the <strong>Search &amp; Reporting Splunk App</strong> in the Splunk console, and use the following SPL query:</p> 
<p><code>index="&lt;YOUR INDEX&gt;" sourcetype="&lt;YOUR SPLUNK SOURCE TYPE&gt;"</code></p> 
<p>The search returns all cloud and client-side metrics generated by AWS IoT Device Defender and to prove that the data is ingested into the chosen index.</p> 
<p>Now write a new SPL query to monitor the <code>aws:num-listening-tcp-ports</code> value over time, by device. Use the following query:</p> 
<p><code>index="&lt;YOUR INDEX&gt;" sourcetype="&lt;YOUR SPLUNK SOURCE TYPE&gt;" | spath name | search name="aws:num-listening-tcp-ports"<br /> | chart max(value.count) as tcp_count over _time by thing</code></p> 
<p>This query demonstrates that the total count of open TCP ports has changed on a single device, which warrants a deeper investigation by a security analyst.</p> 
<p><img alt="Figure 5: Screenshot of the Splunk Cloud Search and Reporting console. It shows that the total count of open TCP ports has changed on a single device" class="aligncenter wp-image-14995 size-full" height="803" src="https://d2908q01vomqb2.cloudfront.net/f6e1126cedebf23e1463aee73f9df08783640400/2024/03/20/IOTB-742_figure_5.png" width="1274" /></p> 
<p><em>Figure 5: Displaying total number of open TCP ports</em></p> 
<p>Using the name of the device exhibiting suspicious behavior, run another SPL query to determine which ports may be open.</p> 
<p><code>index="&lt;YOUR INDEX&gt;" sourcetype="&lt;YOUR SPLUNK SOURCE TYPE&gt;" | where thing="&lt;YOUR THING NAME&gt;"<br /> | spath name<br /> | search name="aws:listening-tcp-ports"<br /> | spath value.ports{} output=open-ports<br /> | mvexpand open-ports<br /> | chart count(open-ports) over _time by open-ports</code></p> 
<p><img alt="Figure 6: Screenshot of the Splunk Cloud Search and Reporting console. It shows that TCP port 21 was opened on the device." class="aligncenter wp-image-14989 size-full" height="599" src="https://d2908q01vomqb2.cloudfront.net/f6e1126cedebf23e1463aee73f9df08783640400/2024/03/20/IOTB-742_figure_6.png" width="1335" /></p> 
<p><em>Figure 6: Displaying open TCP ports on device</em></p> 
<p>The security analyst can now further interrogate other data points, such as <code>aws:all-packets-out</code> or <code>aws:all-bytes-out</code>, to see if there may be other data exfiltration indicators. These data points can be assessed alongside data from other devices (such as network switches, routers, and workstations) to provide a complete picture of what might have happened to this device and the level of risk posed to the organization.</p> 
<h3>Audits</h3> 
<p>Audits can be scheduled or run immediately. In the <strong>AWS IoT Core console</strong>, navigate to <strong>Audit</strong>, then <strong>Results</strong>, and choose <strong>Create</strong>. Select <strong>Available checks</strong> and select <strong>Run audit now (once)</strong>, under <strong>Set schedule</strong>, and choose <strong>Create</strong>.</p> 
<p>The security analyst can track the status of the historical audit reports over time using SPL similar to the following:</p> 
<p><code>index="&lt;YOUR INDEX&gt;" sourcetype="&lt;YOUR SPLUNK SOURCE TYPE&gt;" | where isnotnull(checkName)</code></p>

<p><em>Figure 7: Displaying audit reports</em></p> 
<h2>Conclusion</h2> 
<p>This post demonstrated how AWS IoT Device Defender’s export metrics and audit features, together with Amazon Data Firehose and Splunk’s platform can be used to ingest security data from IoT devices at scale. By using SIEM solutions, such as the Splunk Platform, SOC analysts can assess the risk to the business from deployed IoT devices, and make informed decisions on how to best safeguard business continuity. To learn more about how AWS IoT Device Defender can be used to manage the security of your IoT fleet, see <a href="https://docs.aws.amazon.com/iot/latest/developerguide/device-defender.html">AWS IoT Device Defender</a>.</p>
