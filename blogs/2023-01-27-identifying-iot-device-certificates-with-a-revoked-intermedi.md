<h2>Introduction</h2> 
<p>Dynamically verifiable device identity is a <a href="https://aws.amazon.com/blogs/iot/how-to-implement-zero-trust-iot-solutions-with-aws-iot-3/">foundational component</a> of a Zero Trust Architecture (ZTA). Ongoing dynamic evaluation of identity and trust requires complete and timely visibility into relevant components of that identity. Active device certificates issued by a revoked intermediate Certificate Authority (CA) can pose a security threat due to the intermediate CA being potentially compromised. Previously, there had been no ready-made solution to identify active device certificates that were issued by a revoked intermediate CA.</p> 
<h2>Background</h2> 
<p><img alt="" class="size-full wp-image-11755 aligncenter" height="423" src="https://d2908q01vomqb2.cloudfront.net/f6e1126cedebf23e1463aee73f9df08783640400/2023/01/26/figure1.png" width="540" /></p> 
<p><em>Figure 1. Hierarchical public key infrastructure (PKI) chain including root CA, intermediate CA, and IoT device certificates issued by an intermediate CA.</em></p> 
<p><a href="https://aws.amazon.com/iot-core/">AWS IoT Core</a> customers can use <a href="https://en.wikipedia.org/wiki/X.509">X.509 certificates</a> to authenticate client and device connections. These certificates can be generated by AWS IoT, or signed by a CA, irrespective of whether the CA is registered with AWS IoT.</p> 
<p>In most practical applications, intermediate CAs issue device certificates as this approach <a href="https://docs.aws.amazon.com/privateca/latest/userguide/ca-best-practices.html">provides an additional layer of security</a> and helps manage security incidents gracefully. For example, in case of a suspected security incident with a device or group of devices, only the intermediate CA can be revoked instead of revoking the root certificate. When the intermediate CA is revoked, all device certificates that are in the same chain as the revoked intermediate CA are revoked automatically. This approach limits the cost and impact of the security incident.</p> 
<p>Previously, AWS IoT Core customers who <a href="https://docs.aws.amazon.com/iot/latest/developerguide/device-certs-your-own.html">brought their own device certificates</a> backed by an external multi-level Public Key Infrastructure (PKI) hierarchy had no ready-made solution to identify active AWS IoT Core certificates issued by a revoked intermediate CA. These customers needed to build custom solutions to gain required visibility, or they risked being exposed to potential threats stemming from unmonitored usage of possibly compromised device credentials.</p> 
<h2>Solution</h2> 
<p>Customers using their own device certificates needed an automated mechanism to identify certificates with a revoked intermediary CA. With the new <a href="https://aws.amazon.com/about-aws/whats-new/2022/11/aws-iot-device-defender-audit-check-revoked-intermediate-certificate-authority/">CA chain audit check</a>, <a href="https://aws.amazon.com/iot-device-defender/">AWS IoT Device Defender</a> addresses this gap. AWS IoT Device Defender, a fully managed service for auditing and monitoring devices connected to AWS IoT, supports checking for active certificates issued by a revoked intermediate CA. When a potentially compromised intermediate CA is revoked, all active certificates issued by that intermediate CA are identified as non-compliant, failing the associated audit check.</p> 
<p>The new check makes it easier for customers to identify affected certificates using relevant X.509 certificate extension declarations and <a href="https://aws.amazon.com/blogs/security/choosing-the-right-certificate-revocation-method-in-acm-private-ca/">standard certificate revocation methods</a>, such as Certificate Revocation Lists (CRLs) and Online Certificate Status Protocol (OCSP). You can use the new audit check as part of a broader <a href="https://aws.amazon.com/blogs/iot/improve-your-security-posture-with-aws-iot-device-defender-direct-integration-with-aws-security-hub/">integrated AWS IoT Device Defender and AWS Security Hub architecture</a> to continuously audit, monitor, and remediate your Internet of Things (IoT) devices in accordance with the core principles of ZTA.</p> 
<h2>How to identify active device certificates with a revoked intermediate CA</h2> 
<p>The new audit check leverages standard revocation check methods whilst being able to traverse public key infrastructure (PKI) hierarchies. It relies on the information provided via relevant X.509 certificate extensions to discover the PKI CA hierarchy and perform the associated certificate revocation checks.</p> 
<p>In our sample scenario shown in Figure 2, this audit check occurs as the following sequence:</p> 
<ol> 
 <li>Root CA or intermediate CA revokes the target intermediate CA certificate, where the intermediate CA is the issuer of a certificate actively used by an IoT device interacting with AWS IoT Core.</li> 
 <li>Customer initiates an AWS IoT Device Defender audit, which includes the revoked intermediate CA audit check.</li> 
 <li>AWS IoT Device Defender performs the revocation check using the available revocation check method, in accordance with the hierarchy of the associated PKI.</li> 
 <li>If a revoked intermediate CA is identified, the audit generates a non-compliant “Intermediate CA revoked for active device certificates” finding.</li> 
</ol> 
<p><img alt="" class="alignnone wp-image-11756" height="487" src="https://d2908q01vomqb2.cloudfront.net/f6e1126cedebf23e1463aee73f9df08783640400/2023/01/26/figure2.png" width="1011" /></p> 
<p><em>Figure 2. AWS IoT Device Defender revoked intermediate CA audit check flow.</em></p> 
<p>To use this feature, you can access the <a href="https://console.aws.amazon.com/iot/home?region=us-west-2#/dd/auditIntro">Device Defender audit section</a> within your AWS Console and enable the new audit check. If you have not enabled Device Defender audit, you can do it with <a href="https://console.aws.amazon.com/iot/home?#/dd/auditIntro">one-click using Automate IoT security audit</a> on Device Defender to help secure your IoT devices.</p> 
<p><img alt="" class="size-full wp-image-11757 aligncenter" height="572" src="https://d2908q01vomqb2.cloudfront.net/f6e1126cedebf23e1463aee73f9df08783640400/2023/01/26/figure3.png" width="967" /></p> 
<p><em>Figure 3. AWS IoT Device Defender audit section.</em></p> 
<p>The check handles device certificates that have an issuer endpoint declared in the relevant X.509 extension, and reports active certificates issued by a revoked intermediate CA. You can disable the compromised device certificate using a pre-built mitigation action or initiate a custom mitigation through an AWS Lambda function. More documentation on AWS IoT Device Defender intermediate CA audit check can be <a href="https://docs.aws.amazon.com/iot/latest/developerguide/audit-chk-active-intermediary-device-revoked-CA.html">found here</a>.</p> 
<p>Customer device certificates used with&nbsp;AWS IoT Core need to include the necessary&nbsp;Authority Information Access (AIA) details required to perform the underlying CA revocation checks:</p> 
<p><img alt="" class="wp-image-11758 aligncenter" height="498" src="https://d2908q01vomqb2.cloudfront.net/f6e1126cedebf23e1463aee73f9df08783640400/2023/01/26/figure4.jpg" width="1379" /></p> 
<p><em>Figure 4. X.509 certificate extension declarations showing certificate Authority Information Access (AIA) and CRL endpoint details.</em></p> 
<p>Subsequently, the <em>Intermediate CA revoked for active device certificates audit check</em> can be used to identify any active device certificates issued by the revoked intermediate CA.</p> 
<p><img alt="" class="size-full wp-image-11759 aligncenter" height="457" src="https://d2908q01vomqb2.cloudfront.net/f6e1126cedebf23e1463aee73f9df08783640400/2023/01/26/figure5.jpg" width="1590" /></p> 
<p><em>Figure 5. Selecting the Intermediate CA revoked for active device certificates audit check as part of new audit creation process.</em></p> 
<p>The check can leverage the AIA details and published certificate revocation information, whilst traversing the associated PKI hierarchy to determine the intermediate CA revocation status. In this test example, we can see that an intermediate CA used to issue device certificates was revoked by the root CA:</p> 
<p><img alt="" class="wp-image-11760 aligncenter" height="457" src="https://d2908q01vomqb2.cloudfront.net/f6e1126cedebf23e1463aee73f9df08783640400/2023/01/26/figure6.jpg" width="1381" />.</p> 
<p><em>Figure 6. Example Certificate Revocation List (CRL) entry showing a revoked certificate corresponding to the intermediate CA.</em></p> 
<p>Upon revocation, a previously compliant audit check would fail, because AWS IoT Device Defender identifies a revoked intermediate CA.</p> 
<p><img alt="" class="size-full wp-image-11761 aligncenter" height="237" src="https://d2908q01vomqb2.cloudfront.net/f6e1126cedebf23e1463aee73f9df08783640400/2023/01/26/figure7.jpg" width="1570" /></p> 
<p><em>Figure 7. AWS IoT Device Defender Audit Result showing non-compliant audit finding.</em></p> 
<p>The associated finding provides additional information about the impacted device certificates, as well as the affected issuer identifier registered with AWS IoT Core.</p> 
<p><img alt="" class="size-full wp-image-11762 aligncenter" height="542" src="https://d2908q01vomqb2.cloudfront.net/f6e1126cedebf23e1463aee73f9df08783640400/2023/01/26/figure8.jpg" width="1583" /></p> 
<p><img alt="" class="size-full wp-image-11763 aligncenter" height="252" src="https://d2908q01vomqb2.cloudfront.net/f6e1126cedebf23e1463aee73f9df08783640400/2023/01/26/figure8a.jpg" width="1585" /></p> 
<p><em>Figure 8. Additional information provided as part of the associated Intermediate CA revoked for active device certificates audit finding.</em></p> 
<p>You can now identify client or device certificates that have their issuing CA revoked in a CA chain via a scheduled audit automatically, or initiate an ad-hoc AWS IoT Device Defender audit report manually as needed.</p> 
<p>If non-compliant certificates are identified, you can initiate a pre-built mitigation action, such as disabling the affected device certificate or initiate a custom mitigation action through a Lambda function.</p> 
<h2>Conclusion</h2> 
<p>IoT devices using device certificates issued by a revoked intermediate CA can pose a security threat to your IoT solution. AWS recommends identifying active devices issued by a revoked intermediate CA and taking actions such as disabling or replacing these device certificates.</p> 
<p>This recommendation aligns with one of the core principles of ZTA of continuously monitoring and measuring the integrity and security posture of your IoT devices and verifying device trust on an ongoing basis.</p> 
<p>Using the new AWS IoT Device Defender audit check feature, customers can continuously audit, monitor, and remediate affected device identities, such as:</p> 
<ol> 
 <li>Provision new certificates, that are signed by a different CA, for the affected devices.</li> 
 <li>Verify that the new certificates are valid, and that the devices can use them to connect.</li> 
 <li>Initiate built-in AWS IoT Device Defender <a href="https://docs.aws.amazon.com/iot/latest/developerguide/dd-mitigation-actions.html">mitigation actions</a> or custom mitigation actions through a Lambda function, if required. Customers can perform these mitigation actions by calling the <a href="https://docs.aws.amazon.com/iot/latest/apireference/API_StartAuditMitigationActionsTask.html">AWS IoT Device Defender API</a> or <a href="https://awscli.amazonaws.com/v2/documentation/api/latest/reference/iot/start-audit-mitigation-actions-task.html">AWS CLI</a> directly.</li> 
</ol> 
<p>The new audit check makes it easier for customers to identify affected certificates, helping to improve the overall security posture of your IoT solutions.</p>
